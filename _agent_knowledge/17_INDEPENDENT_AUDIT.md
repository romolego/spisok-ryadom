# 17_INDEPENDENT_AUDIT

> Исторический снимок версии 0.2.0. Исправления IA01–IA07 и финальная проверка 0.2.1: `18_AUDIT_FIX_VERIFICATION.md`. Результаты ниже относятся к состоянию до этих исправлений.

## Независимый аудит 0.2.0 — 17 октября 2026

Текущая готовность не подтверждена: независимый аудит HEAD f09eebe нашёл 7 проблемных сценариев IA01–IA07. Прежние 30 тестов проходят; из 14 дополнительных проверок 12 воспроизводят ошибки, 2 контрольных теста фокуса проходят. Код приложения и выданный APK не изменялись.

Критично IA01: legacy JSON схлопывает разные одноимённые записи одной копии и теряет поля. Другие подтверждённые проблемы: раннее закрытие/commit inline-редактора количества (плюс дефект фильтра запятой по коду), перекрытый picker товаров магазина, stale whole-row update при переносе покупки, шаг от другой единицы, разный выбор строки отображением/командой каталога и несовместимость старого написания unit после миграции. Подробности и конкретные воспроизведения: `17_INDEPENDENT_AUDIT.md`.

Прежняя успешная проверка в 16 остаётся фактом выполнения своего набора, но не доказательством отсутствия этих ошибок. Описания поставки ниже читать с этим ограничением. На физическом телефоне APK по-прежнему не проверен.

## IA01 · P1 · Старый импорт теряет разные одноимённые записи

Два разных товара «Молоко, л» с разными получателями и заметками превращаются в один. Один набор полей затирается; связи объединяются. Два магазина одной сети без адреса также схлопываются.

На пустой установке импортировать JSON v3 с двумя разными product ID, одинаковыми name/defaultUnit, разными recipientId/note. Аналогично — два shop ID с одинаковыми name и пустым address.

Поиск совпадения выполняется в уже изменяемой базе на каждой строке. Вторая запись сопоставляется с первой, только что вставленной из того же файла.

Исправление: Сохранять отдельность source ID внутри одного импорта; сопоставление с существующим каталогом выполнять по снимку до импорта и подтверждать неоднозначности.

- `app/src/main/java/com/spisokryadom/app/data/backup/BackupManager.kt:114–117`
- `app/src/main/java/com/spisokryadom/app/data/backup/BackupManager.kt:105–106`

Проверки: `legacyImportPreservesDifferentSourceProductsWithSameNameAndUnit`, `legacyImportPreservesDifferentSourceShopsWithSameNameAndNoAddress`.

## IA02 · P2 · Быстрый редактор количества закрывается сразу

После нажатия числа в каталоге редактор исчезает до ввода. Изолированный компонент дополнительно проверен без навигации/БД. В том же компоненте статически найден второй дефект: фильтр удаляет запятую, превращая 0,5 в 05; сквозной ввод до него не доходит из-за первой ошибки.

Добавить 3 кг, открыть вкладку «Товары» и нажать число. Проверить, что остаётся редактируемое поле, а сохранение без ввода не вызывается.

Первое событие onFocusChanged(false) принимается за потерю уже полученного фокуса: вызывается onSetQuantity и isEditing=false раньше LaunchedEffect.requestFocus. Отдельно фильтр пропускает только цифры и точку.

Исправление: Игнорировать unfocused до первого фактического focus=true; сохранять десятичную запятую и валидировать ввод без удаления значимых символов.

- `app/src/main/java/com/spisokryadom/app/ui/components/CommonComponents.kt:685–689`
- `app/src/main/java/com/spisokryadom/app/ui/components/CommonComponents.kt:721–729`
- `app/src/main/java/com/spisokryadom/app/ui/components/CommonComponents.kt:694–696`

Проверки: `inlineQuantityEditorMustRemainOpenForDecimalInput`, `tappingQuantityMustOpenEditorWithoutCommitting`.

## IA03 · P2 · Выбор товаров магазина перекрыт основным экраном

Кнопка «Добавить из базы товаров» создаёт список под основным экраном. Пользователь не видит кандидатов и не может поставить их чекбоксы обычным нажатием.

Создать магазин без привязок и товар в каталоге; открыть магазин, нажать «Добавить из базы товаров», физически нажать чекбокс кандидата.

PickProductsDialog является обычным Scaffold и рисуется перед ещё одним полноэкранным Scaffold. Нет отдельного окна или ветки else.

Исправление: Показывать picker отдельным экраном/настоящим Dialog либо единственной веткой содержимого. Проверять pointer hit testing, а не только наличие semantics.

- `app/src/main/java/com/spisokryadom/app/ui/shopcontent/ShopContentScreen.kt:69–83`
- `app/src/main/java/com/spisokryadom/app/ui/shopcontent/ShopContentScreen.kt:207–215`

Проверки: `visiblePickerCheckboxMustReceivePhysicalTap`.

## IA04 · P2 · Перенос покупки может отменить другие изменения

При допустимом чередовании команд смена магазина возвращает старое количество и статусы «Куплено»/«Срочно».

Начать changeShop; после чтения строки изменить её количество/статусы; продолжить смену магазина. Тест реального ViewModel детерминированно приостанавливает DAO только для задания этого порядка.

ViewModel читает старый объект вне транзакции, делает дополнительные suspend-запросы и передаёт целую копию в @Update. Транзакция вокруг последней записи не защищает раннее чтение.

Исправление: Менять только целевые поля атомарной командой либо читать и вычислять новую строку в одной транзакции. Добавить тесты смешанных команд.

- `app/src/main/java/com/spisokryadom/app/ui/shoppinglist/ShoppingListViewModel.kt:493–527`
- `app/src/main/java/com/spisokryadom/app/data/repository/ShoppingListRepository.kt:81–81`

Проверки: `movingShopMustPreserveConcurrentQuantityBoughtAndUrgencyChanges`.

## IA05 · P2 · Шаг количества переносится между разными единицами

При defaultQuantity=100/defaultUnit=шт покупка 0,5 кг после «+» становится 100,5 кг.

В карточке товара задать 100 шт по умолчанию; добавить этот же товар через текстовый список как 0,5 кг; нажать «+».

defaultQuantity используется как шаг без сравнения defaultUnit товара с unit конкретной покупки. Само решение о шаге по умолчанию предусмотрено D-040, ошибка в размерности.

Исправление: Использовать defaultQuantity только при совместимых единицах; для другой единицы применять отдельно заданный/предсказуемый шаг.

- `app/src/main/java/com/spisokryadom/app/ui/shoppinglist/ShoppingListViewModel.kt:580–588`
- `app/src/main/java/com/spisokryadom/app/ui/productdb/ProductDatabaseViewModel.kt:51–52`
- `app/src/main/java/com/spisokryadom/app/ui/shopcontent/ShopContentViewModel.kt:141–142`

Проверки: `quantityStepMustNotUseDefaultNumberFromAnotherUnit`.

## IA06 · P2 · Контрол каталога может менять скрытую покупку

При нескольких покупках одного товара показывается одна строка, а «+» меняет другую. Воспроизводится при расхождении порядка ID и createdAt, например после коррекции часов.

У одного продукта создать id1: 1 кг, createdAt=2000; id2: 2 шт, createdAt=1000. Каталог показывает id1; нажатие «+» меняет id2.

Отображение выбирает минимальный id, команда заново ищет по productId и берёт первую строку по createdAt. Известный UI entryId игнорируется.

Исправление: Передавать entryId из отображаемого ShoppingListInfo непосредственно в команды количества.

- `app/src/main/java/com/spisokryadom/app/ui/productdb/ProductDatabaseViewModel.kt:41–42`
- `app/src/main/java/com/spisokryadom/app/ui/productdb/ProductDatabaseViewModel.kt:51–53`
- `app/src/main/java/com/spisokryadom/app/data/repository/ShoppingListRepository.kt:58–60`

Проверки: `catalogQuantityControlMustModifyTheEntryItDisplays`.

## IA07 · P2 · Старые написания единиц дробят совместимые покупки

После миграции v7→v8 покупка 2 КГ. и новое добавление 1 кг остаются двумя строками вместо одной на 3 кг.

Мигрировать настоящую схему 7 со строкой unit=КГ., затем вызвать новое addProduct того же товара с unit=кг.

Новые единицы нормализуются, сохранённые старые не нормализуются; SQL findCompatible сравнивает строки буквально.

Исправление: Канонизировать сохранённые единицы с безопасным объединением совместимых строк либо сравнивать каноническое представление.

- `app/src/main/java/com/spisokryadom/app/data/db/AppDatabase.kt:113–129`
- `app/src/main/java/com/spisokryadom/app/data/dao/ShoppingListEntryDao.kt:71–72`
- `app/src/main/java/com/spisokryadom/app/data/repository/ShoppingListRepository.kt:30–32`

Проверки: `migratedLegacyUnitSpellingStillMergesWithNormalizedNewPurchase`.

## Производительность и ограничения

Обычная прокрутка не признана медленной: аппаратные FPS не измерялись. Синтетический разрешённый длинный ввод для 5001 названия занимает 18,64 с / 16,63 с в JVM. Bulk блокирует выход во время обработки, Levenshtein не имеет раннего отсечения/проверки отмены. Это отдельный крайний сценарий, не доказательство обычных фризов телефона.

Export держит транзакцию во время упаковки фотографий; задержка конкурирующих записей на большом архиве не измерялась.

Резервная копия полного ZIP не объявляется полностью доказанной для всех случаев. Новых подтверждённых дефектов потери данных в full restore этот аудит не нашёл.

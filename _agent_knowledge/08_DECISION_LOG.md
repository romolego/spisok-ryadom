- **Что решено:** по прямому запросу пользователя от 2026-10-16 накопленные исходники, knowledge-база и рабочие материалы сохраняются в новой ветке `codex/publish-local-state-2026-10-16` репозитория `romolego/spisok-ryadom`.
- **Почему:** проверка `git ls-remote` и `git fetch` показала, что на GitHub есть только `main` на `ca676cb020a67e0a9516db69e4cf3151c6da4fe2` от 2026-03-25, а последующие изменения остались в рабочем дереве.
- **Влияние:** `main` не переписывается; `.kotlin/` и временные файлы Office исключены через `.gitignore`. APK, локальные пути SDK и ключи подписи не входят в публикуемый снимок. Сравнение APK служит дополнительным ориентиром, а свежая сборка оценивается отдельно от факта публикации исходников.

## D-001. Один общий текущий список в первой версии

- **Что решено:** в первой версии используется один общий текущий список покупок.
- **Почему:** это упрощает модель и позволяет закрыть потребности через группировки, фильтры и представления, а не через множество параллельных списков.
- **Влияние:** агент не должен вводить несколько текущих списков без отдельного нового решения.

## D-002. Все данные хранятся локально

- **Что решено:** данные приложения хранятся локально на устройстве.
- **Почему:** это часть базовой концепции продукта и требования к работе без интернета.
- **Влияние:** первая версия не должна требовать серверную часть как обязательную основу.

## D-003. Целевая публикация — RuStore

- **Что решено:** проект делается как Android-приложение с расчётом на публикацию в RuStore.
- **Почему:** это целевая модель выпуска, зафиксированная в концепции.
- **Влияние:** приложение должно оставаться понятным, стабильным и без лишних разрешений.

## D-004. Проект ведётся строго итерациями

- **Что решено:** работа идёт через узкие изолированные итерации.
- **Почему:** пользователь не программист, а проект нужно удерживать управляемым и проверяемым.
- **Влияние:** агент не должен смешивать несколько крупных несвязанных задач в одном изменении.

## D-005. Пользовательские классификаторы задаёт сам пользователь

- **Что решено:** получатели, группы товаров, единицы измерения, названия магазинов и названия отделов не должны быть жёстко зашиты как пользовательские значения.
- **Почему:** приложение должно быть гибким и пригодным для широкой аудитории.
- **Влияние:** агент не должен вводить фиксированные пользовательские списки там, где концепция требует пользовательского ввода.

## D-006. Приоритетный магазин используется как магазин по умолчанию

- **Что решено:** если у товара задан приоритетный магазин, при добавлении из общего контекста он подставляется как магазин по умолчанию.
- **Почему:** это ускоряет главный бытовой сценарий и поддерживает работу с товарами, которые доступны в нескольких магазинах.
- **Влияние:** связь товара с магазином должна хранить приоритет, а не сводиться к одному полю магазина в карточке товара.

## D-007. Новые позиции можно создавать из любого места, но это не основной сценарий

- **Что решено:** новая карточка товара может создаваться из разных представлений, но основной сценарий всё равно строится вокруг выбора из уже существующей базы.
- **Почему:** так сохраняется скорость бытового использования и снижается количество дублей.
- **Влияние:** UI не должен продвигать постоянное создание новых карточек как главный путь взаимодействия.

## D-008. Основная среда разработки — Claude Code

- **Что решено:** основной средой агентской разработки считается Claude Code.
- **Почему:** это часть согласованного рабочего процесса проекта.
- **Влияние:** документация должна явно учитывать этот контекст, не исключая при этом другие агенты.

## D-009. Codex и Cursor используются как вспомогательные агенты

- **Что решено:** Codex и Cursor используются как вспомогательные ИИ-инструменты.
- **Почему:** проект допускает работу несколькими агентами, но на общей knowledge-базе.
- **Влияние:** любой агент обязан ориентироваться на одну и ту же агентскую инфраструктуру внутри репозитория.

## D-010. База знаний должна оставаться tool-neutral

- **Что решено:** проектная knowledge-инфраструктура не должна зависеть от одного конкретного агентского инструмента.
- **Почему:** над проектом могут работать Claude Code, Codex, Cursor и другие агенты, и все они должны видеть один и тот же контекст.
- **Влияние:** нельзя писать правила, которые скрыто завязаны только на один агентский интерфейс или одну терминологию.

## D-011. Магазины могут быть как с отделами, так и без них

- **Что решено:** у магазина может быть набор отделов, но наличие отделов не является обязательным.
- **Почему:** в реальной жизни часть торговых точек имеет внутреннюю структуру, а часть нет.
- **Влияние:** модель и UI должны поддерживать оба варианта без усложнения базового сценария.

## D-012. Купленные позиции не удаляются автоматически сразу

- **Что решено:** купленная позиция по умолчанию не исчезает моментально из текущего списка.
- **Почему:** это помогает в реальном походе по магазину и снижает риск ошибочного исчезновения нужной позиции.
- **Влияние:** интерфейс должен поддерживать состояние купленной позиции и отдельную очистку купленных записей.

## D-013. Технологический стек первой версии — Kotlin + Compose + Room

- **Что решено:** первая версия реализована на Kotlin с Jetpack Compose (Material 3), Room (SQLite), Compose Navigation и MVVM (ViewModel + StateFlow).
- **Почему:** Compose — современный стандарт для новых Android-проектов, хорошо интегрируется с ViewModel, Navigation и Room, требует меньше boilerplate для списков и форм. Проект начинается с нуля, нет legacy XML.
- **Влияние:** все экраны реализуются как Composable-функции, данные передаются через StateFlow, навигация через Compose Navigation.

## D-014. Manual DI (AppContainer) вместо Hilt

- **Что решено:** DI реализован через ручной AppContainer в Application subclass, без Hilt/Dagger.
- **Почему:** в приложении одна база данных, 4 репозитория и 5 ViewModel — ручной контейнер проще и не требует annotation processing через kapt/ksp для DI. При росте приложения можно мигрировать на Hilt.
- **Влияние:** ViewModels получают зависимости через ViewModelProvider.Factory, обращаясь к AppContainer.

## D-015. purchaseType хранится как String

- **Что решено:** тип покупки (онлайн/оффлайн) хранится в Room как String ("offline"/"online"), а не как Room enum.
- **Почему:** forward-compatibility — при добавлении новых типов не потребуется миграция базы.
- **Влияние:** UI использует radio-кнопки для выбора, бизнес-логика сравнивает строки.

## D-016. Фото товара — URI-строка без интеграции с камерой/галереей в v1

- **Что решено:** поле `photoUri` заложено в модели ProductEntity, но в первой итерации UI показывает текстовое поле для ввода URI, без камеры/галереи.
- **Почему:** интеграция с камерой и галереей усложняет первую итерацию без критической необходимости.
- **Влияние:** камера/галерея будут добавлены в следующих итерациях.

## D-017. История отложена из каркаса первой итерации

- **Что решено:** сущности истории (HistorySnapshot, HistoryEntry) не включены в Room-базу первой итерации.
- **Почему:** каркас первой итерации фокусируется на рабочих сущностях (товары, магазины, текущий список). История — задел, который можно добавить позже без ломки основной модели.
- **Влияние:** при добавлении истории потребуется Room-миграция (добавление новых таблиц).

## D-018. Текущий список группируется по магазинам как основное представление

- **Что решено:** главный экран текущего списка показывает позиции, сгруппированные по магазинам (по displayOrder), с группой «Без магазина» в конце.
- **Почему:** представление по магазинам — главный рабочий сценарий приложения (пройтись по магазинам и отмечать купленное).
- **Влияние:** сортировка внутри группы: срочные некупленные → обычные некупленные → купленные.

## D-019. Демо-данные через SharedPreferences с лёгким отключением

- **Что решено:** демо-данные заполняются при первом запуске через DemoDataProvider с флагом в SharedPreferences. Повторная загрузка не происходит.
- **Почему:** нужно показать приложение как рабочий продукт с адекватной тестовой картиной. Механизм легко отключить комментированием одной строки или вызовом resetDemoFlag.
- **Влияние:** при необходимости сброса данных: вызвать DemoDataProvider.resetDemoFlag() и пересоздать БД.

## D-020. Единицы измерения — подсказки вместо жёсткого справочника

- **Что решено:** при вводе единицы измерения показываются уже существующие значения из базы как подсказки. Пользователь может ввести любое новое значение.
- **Почему:** концепция требует модели рекомендаций, а не жёсткого закрытого справочника.
- **Влияние:** компонент QuantityUnitInputWithSuggestions используется в карточке товара и в диалоге добавления в список.

## D-021. Быстрый перенос между магазинами с автоподстановкой отдела

- **Что решено:** при переносе позиции в другой магазин сначала проверяются product-shop links для отдела, затем ищется одноимённый отдел в новом магазине.
- **Почему:** ускоряет сценарий «не нашёл товар — переношу в другой магазин» с минимумом действий.
- **Влияние:** допустимые магазины (из product-shop links) показываются первыми в диалоге переноса.

## D-023. Количество и единица в записи списка независимы от карточки товара

- **Что решено:** поля quantity и unit в ShoppingListEntryEntity — это фактические значения конкретной покупки, независимые от defaultQuantity/defaultUnit в ProductEntity. Редактирование этих полей у записи списка не меняет карточку товара.
- **Почему:** пользователь часто покупает товар в разном количестве, и изменение количества для одной покупки не должно влиять на дефолтные настройки карточки.
- **Влияние:** при добавлении товара в список дефолтные значения используются как стартовая подстановка. Дальше пользователь редактирует количество прямо из списка через диалог, без необходимости заходить в карточку товара.

## D-024. Основное действие записи списка — работа с текущей покупкой, а не с карточкой товара

- **Что решено:** количество товара в текущем списке можно быстро менять прямо в карточке записи через встроенный блок «−/количество/+», без открытия диалога. Короткий тап по основной зоне карточки открывает диалог редактирования записи (ручной ввод количества, магазин, заметка) как дополнительный сценарий. Карточка товара и удаление доступны через long press контекстное меню.
- **Почему:** наиболее частое действие — изменение количества на ±шаг (шаг = defaultQuantity товара или 1). Открытие диалога только ради этого было избыточным. Встроенный блок ускоряет главный бытовой сценарий, а диалог остаётся для ручного ввода произвольного количества и работы с заметкой.
- **Влияние:** ShoppingListItem содержит встроенный Row с IconButton (−), Text (количество+единица), IconButton (+) вместо статичного бейджа количества. ViewModel получил методы increaseQuantity/decreaseQuantity. Кнопка «−» заблокирована при quantity ≤ шага и для купленных. Диалог редактирования остаётся доступным через тап по основной зоне карточки.

## D-025. Перестановка и сворачивание магазинных блоков в текущем списке

- **Что решено:** в режиме «по магазинам» пользователь может менять порядок магазинных блоков кнопками вверх/вниз и сворачивать/разворачивать блоки кликом по заголовку. Порядок сохраняется через displayOrder в Room, состояние сворачивания — в SharedPreferences.
- **Почему:** основной рабочий сценарий — прохождение по магазинам в удобном порядке. Перестановка позволяет настроить маршрут покупок. Сворачивание уменьшает визуальный шум, когда часть магазинов уже пройдена или не актуальна.
- **Влияние:** ShopDao получил метод updateAll для пакетного обновления порядка. EntryGroup расширен полями isCollapsed, totalCount, boughtCount. Блок «Без магазина» всегда последний и не перемещается. Функциональность ограничена режимом «по магазинам».

## D-022. Четыре переключаемых представления текущего списка

- **Что решено:** текущий список поддерживает 4 режима представления одних и тех же данных: по магазинам, по группам товаров, по получателям, общий без группировки. Режим переключается через FilterChip-панель и сохраняется в SharedPreferences.
- **Почему:** концепция требует нескольких представлений (06_FUNCTIONAL_REQUIREMENTS), но как разные виды одного общего списка, а не как отдельные списки. Представление по магазинам остаётся главным.
- **Влияние:** модель ShopGroup обобщена до EntryGroup; ShoppingListEntryUi расширен полями groupName и recipientName; ViewModel получил зависимость от ClassifierRepository; очистка купленных по группе работает только в режиме «по магазинам».

## D-026. Фильтр «Только срочные» показывает только активные срочные позиции

- **Что решено:** режим «Только срочные» показывает только позиции `isUrgent && !isBought` и не подмешивает купленные записи.
- **Почему:** подпись фильтра и счётчик должны совпадать с фактическим набором позиций, иначе возникает логическая путаница.
- **Влияние:** фильтрация в ShoppingListViewModel приведена к строгому набору «срочные и не купленные».

## D-027. Поведение срочных позиций в свёрнутых магазинах управляется настройкой

- **Что решено:** в режиме «по магазинам» добавлен отдельный переключатель «Срочные в свёрнутых»; по умолчанию выключен.
- **Почему:** жёстко зашитое поведение в свёрнутых блоках воспринимается как нелогичное. Пользователю нужен явный и понятный контроль.
- **Влияние:** значение сохраняется в `shopping_list_prefs` и восстанавливается после перезапуска; при включении в свёрнутых блоках показываются только срочные некупленные позиции.

## D-029. Справочные блоки в служебных настройках работают по единому паттерну

- **Что решено:** получатели, товарные группы, единицы измерения и группы магазинов в служебных настройках приведены к единому паттерну: обычный режим просмотра (без управляющих действий) и режим правок (переименование, удаление, перемещение вверх/вниз, добавление). Для каждой сущности доступен просмотр использования (в каких товарах или магазинах она применяется).
- **Почему:** до этого решения каждый справочный блок имел свой способ управления — у одних были видны кнопки всегда, у других не было добавления, перемещение отсутствовало у всех. Единый паттерн делает интерфейс предсказуемым и снижает когнитивную нагрузку.
- **Влияние:** ProductGroupEntity и RecipientEntity получили поле displayOrder и Room-миграцию 3→4. UnitEntity получила собственную таблицу с displayOrder и Room-миграцию 6→7. Получатели, товарные группы и единицы измерения поддерживают пользовательский порядок (displayOrder) и ручное перемещение вверх/вниз. Группы магазинов сортируются по алфавиту (без displayOrder, т.к. это производная агрегатная сущность). Добавление группы магазина из настроек создаёт отдел во всех существующих магазинах.

## D-030. Порядок магазинов управляется через режим правок на экране списка

- **Что решено:** пользователь управляет порядком магазинов через режим правок на экране «Магазины» (кнопки вверх/вниз), а не через ручной ввод числа в поле «Порядок отображения» в карточке магазина. Поле displayOrder остаётся как внутренняя техническая логика хранения порядка.
- **Почему:** ручной ввод числа для порядка — неочевидная механика для пользователя. Кнопки вверх/вниз в режиме правок — та же понятная модель, которая уже используется для других упорядочиваемых сущностей (справочники в настройках, группы магазина в карточке).
- **Влияние:** поле «Порядок отображения» убрано из карточки магазина. Новые магазины автоматически получают следующий displayOrder. Экран списка магазинов получил кнопку режима правок в TopAppBar и кнопки перемещения в каждой карточке.

## D-031. Магазин — активная точка наполнения товарами

- **Что решено:** экран магазина (ShopContent) стал полноценной точкой входа для добавления товаров. Из магазина можно: (1) создать новый товар с автоматической привязкой к этому магазину; (2) выбрать существующие товары из общей базы через полноэкранный режим с поиском и чекбоксами. Пустое состояние магазина предлагает оба действия вместо пассивной подсказки «привяжите через карточку товара». При создании товара из контекста магазина привязанный магазин визуально отображается в форме создания товара, чтобы пользователь видел контекст привязки до сохранения.
- **Почему:** магазин не должен быть пассивной сущностью, которую можно наполнять только обходным путём через карточку товара. Наполнение магазина — естественное действие пользователя, который стоит в магазине и видит товары.
- **Влияние:** навигация ProductCard получила опциональный параметр `preselectedShopId`; при создании нового товара из магазина автоматически создаётся ProductShopLink; ShopContentViewModel получил режим выбора товаров из общей базы. ProductCardUiState хранит preselectedShopName для отображения в UI.

## D-032. Экран базы товаров поддерживает 4 режима отображения

- **Что решено:** вкладка «Товары» получила 4 режима отображения: по алфавиту (А–Я), по магазинам, по товарным группам, по получателям. Переключение через FilterChip-панель, выбранный режим сохраняется в SharedPreferences (`product_db_prefs`).
- **Почему:** плоский список товаров неудобен при большой базе. Группировка по разным осям делает экран базы товаров полноценным справочником, а не просто списком. Режимы повторяют логику текущего списка, но работают для общей базы, а не для записей одного списка покупок.
- **Влияние:** ProductDatabaseViewModel получил зависимость от ClassifierRepository и SharedPreferences. Добавлен ProductShopLinkDao.getAll() Flow и ProductRepository.getAllShopLinks(). Товары без значения группировки попадают в секцию «Без магазина» / «Без группы» / «Без получателя» в конце списка.

## D-033. Группы магазина доступны на этапе создания нового магазина

- **Что решено:** при создании нового магазина пользователь может сразу добавлять, переименовывать, удалять и менять порядок групп магазина прямо в форме создания. Группы хранятся локально (pendingDepartments) до первого сохранения магазина, после чего записываются в базу вместе с ним.
- **Почему:** модель «сначала создай пустой магазин, потом вернись и донастрой группы» создавала лишний промежуточный шаг и ощущение незавершённости. Группы магазина — неотъемлемая часть структуры магазина, и пользователь должен иметь возможность задать их сразу.
- **Влияние:** ShopCardViewModel получил PendingDepartment и методы работы с pending-списком. ShopCardScreen показывает полноценную секцию групп для новых магазинов. При сохранении все pending-группы записываются в Room.

## D-034. Привязка магазинов доступна на этапе создания нового товара

- **Что решено:** пользователь может добавлять, удалять, переупорядочивать привязки к магазинам и настраивать группу магазина для каждой привязки прямо в форме создания нового товара, без промежуточного сохранения. Привязки хранятся локально (pendingShopLinks) до сохранения товара, после чего записываются в базу вместе с ним.
- **Почему:** предыдущая модель «создай товар → сохрани → зайди снова → настрой магазины» создавала лишний промежуточный шаг и ощущение незавершённости. Привязка к магазинам — неотъемлемая часть карточки товара.
- **Влияние:** ProductCardViewModel получил PendingShopLink и методы для локального управления привязками. ProductCardScreen показывает полноценную секцию привязок для новых товаров, начиная в режиме редактирования. При сохранении все pending-привязки записываются в Room с последовательными приоритетами.

## D-035. Порядок магазинов в привязках товара управляется кнопками вверх/вниз

- **Что решено:** приоритет привязки товара к магазину определяется позицией в списке и меняется через кнопки вверх/вниз. Ручной числовой ввод приоритета убран из диалога добавления магазина. Новый магазин автоматически получает следующий порядковый номер. После любого изменения списка привязок (добавление, удаление, перемещение) приоритеты автоматически пересчитываются в последовательные значения (1, 2, 3, ...) без дублей и пропусков.
- **Почему:** ручной ввод числа для приоритета — неочевидная механика. Кнопки перемещения — та же модель, которая уже используется для магазинов, групп и справочников. Автоматическая перенумерация исключает ситуацию, когда у одного товара несколько магазинов получают одинаковый приоритет.
- **Влияние:** AddShopLinkDialog больше не содержит поле приоритета. ShopLinkEditCard содержит кнопки вверх/вниз. Приоритет записывается как displayOrder при сохранении. ProductCardViewModel содержит приватный метод renumberShopLinkPriorities(), который вызывается после addShopLink, removeShopLink, moveShopLinkUp, moveShopLinkDown.

## D-036. Умная подсказка группы магазина при привязке товара

- **Что решено:** при добавлении магазина или выборе группы магазина для привязки товара система предлагает наиболее вероятную группу на основе уже выбранных групп в других магазинах. Используется точное совпадение по имени, затем приблизительный поиск через FuzzySearch. Подсказка подставляется автоматически, но пользователь может изменить выбор.
- **Почему:** если товар «Молоко» в одном магазине лежит в группе «Молочные», в другом магазине с одноимённой группой ожидается аналогичная привязка. Подсказка экономит время, но не подменяет решение пользователя.
- **Влияние:** loadDepartmentsForShop вычисляет suggestedDepartmentId/suggestedDepartmentReason. AddShopLinkDialog и DepartmentSelectDialog отображают подсказку и позволяют её принять или отклонить.

## D-037. Создание получателей — только через служебные настройки, не из карточки товара

- **Что решено:** inline-сценарий создания нового получателя прямо из поля «Получатель» в карточке товара убран. Получатель в карточке товара только выбирается из уже существующего справочника. Управление справочником получателей (создание, переименование, удаление, перемещение) доступно только через служебные настройки.
- **Почему:** разделение ответственности: карточка товара потребляет справочник, но не создаёт его изнутри. Это снижает сложность формы и делает логику предсказуемой.
- **Влияние:** из `ProductCardScreen` убраны `showNewRecipientDialog` и диалог создания получателя. Из `ProductCardViewModel` убран метод `createRecipient`. `DropdownSelector` для получателя работает без `allowCreate`. `SettingsViewModel.createRecipient` и соответствующий блок в настройках не затронуты.

## D-038. Заголовок карточки товара: сначала название товара, затем режим экрана

- **Что решено:** в режиме редактирования заголовок TopAppBar карточки товара показывает двухстрочный блок: первая строка — название конкретного товара (`titleMedium`), вторая — слово «Редактирование» (`bodySmall`, приглушённый цвет). В режиме создания нового товара заголовок остаётся однострочным: «Новый товар». Если у нового товара ещё нет имени — это не режим редактирования, и «Новый товар» однозначно описывает ситуацию.
- **Почему:** при прокрутке длинной формы карточки пользователь терял контекст — заголовок «Редактирование товара» без названия не давал понять, с каким именно товаром идёт работа. Название товара важнее режима — оно должно быть первым и крупным.
- **Влияние:** изменён только блок `title` в `TopAppBar` экрана `ProductCardScreen.kt`. Логика полей, магазинов, получателей и других блоков не затронута.

## D-039. Смена группы магазина у уже привязанного магазина — прямо из режима просмотра

- **Что решено:** карточка привязанного магазина (`ShopLinkViewCard`) в режиме просмотра секции «Привязанные магазины» стала кликабельной — клик по ней сразу открывает `DepartmentSelectDialog` для смены группы магазина. Пользователю больше не нужно переходить в режим редактирования (иконка карандаша) только ради смены группы магазина.
- **Почему:** предыдущая механика требовала три шага: найти иконку карандаша → войти в режим правок → кликнуть по области магазина. Это неочевидно и воспринималось как «нужно удалить и добавить заново». Смена группы — часто меняемый параметр, доступ к нему должен быть одним кликом.
- **Влияние:** `ShopLinkViewCard` получила параметр `onEditDepartment: (() -> Unit)?`. При передаче колбэка карточка кликабельна и показывает подсказку «Нажмите для выбора группы», если группа не выбрана. Логика `DepartmentSelectDialog` и `updateShopLinkDepartment` не изменилась. Режим правок (`ShopLinkEditCard`) сохранён для перемещения и удаления привязок.

## D-040. Шаг изменения количества через «−»/«+» равен defaultQuantity товара

- **Что решено:** кнопки «−» и «+» в быстром сценарии изменения количества используют `defaultQuantity` карточки товара как шаг. Если `defaultQuantity` не задано, равно нулю или отрицательное — шаг равен 1. Минимальное допустимое количество в ShoppingList равно шагу (кнопка «−» блокируется при quantity ≤ шагу). В ShopContent при достижении 0 запись удаляется из списка (согласованно с уже существующей логикой `setQuantity`).
- **Почему:** без этого пользователь с товаром `defaultQuantity = 100` вынужден был нажимать «+» 99 раз, чтобы перейти с 1 до 100. Шаг должен быть согласован с логикой самого товара.
- **Влияние:** `ShoppingListEntryUi` расширен полем `defaultQuantity: Double?`. `ShoppingListViewModel.increaseQuantity`/`decreaseQuantity` и `ShopContentViewModel.incrementQuantity`/`decrementQuantity` читают `defaultQuantity` через `_products`/`_allProducts` и используют его как шаг. Условие блокировки кнопки «−» в `ShoppingListScreen` изменено с `quantity > 1.0` на `quantity > quantityStep`.

## D-041. Внутри магазина в текущем списке товары группируются по группам магазина

- **Что решено:** в режиме «по магазинам» записи текущего списка внутри каждого магазинного блока отображаются не в порядке добавления, а сгруппированными по группе магазина (назначенному отделу, `assignedDepartmentId`). Порядок под-групп определяется `displayOrder` отдела. Записи без назначенного отдела помещаются в отдельную под-группу в конце магазинного блока. Визуальный разделитель (под-группового заголовка) появляется только при наличии 2+ групп внутри одного магазина.
- **Почему:** линейный порядок по времени добавления смешивал товары разных отделов в одну кучу, что противоречило задаче «пройтись по отделам». Группировка по отделам магазина делает список предсказуемым маршрутом.
- **Влияние:** добавлены `ShopDeptSubGroup` data class и поле `deptSubGroups: List<ShopDeptSubGroup>` в `EntryGroup`. Добавлен `buildDeptSubGroups` в `ShoppingListViewModel`. `buildShopGroups` принимает `departments` параметр и использует `buildDeptSubGroups` вместо плоского `sortEntries`. Плоский `entries` сохранён для логики сворачивания/разворачивания и фильтрации срочных. В `ShoppingListScreen` добавлен `DeptSubGroupHeader` и ветка рендеринга с под-группами (только в BY_SHOPS, только при развёрнутом блоке, только при 2+ под-группах).

## D-042. Одноразовый комментарий к позиции текущего списка отделён от постоянной заметки товара

- **Что решено:** у записи текущего списка (ShoppingListEntryEntity) появилось отдельное поле `comment`, не связанное с `ProductEntity.note`. Комментарий привязан к конкретной позиции текущего списка, удаляется вместе с ней и не восстанавливается при повторном добавлении того же товара. Существующее поле `note` у записи списка сохранено без изменений.
- **Почему:** постоянная заметка карточки товара и одноразовое уточнение к конкретной покупке — разные по смыслу вещи. Пример: товар «Яблоки» с заметкой «красные кисло-сладкие» может иметь комментарий к покупке «Гала» — первое описывает товар в целом, второе — конкретное уточнение для одной покупки.
- **Влияние:** Room-миграция 4→5 (ALTER TABLE). EditEntryDialog получил поле «Комментарий к покупке». В карточке записи комментарий отображается отдельной строкой с визуальным маркером.

## D-043. Кнопка «+» на главной странице открывает отдельный сценарий добавления позиции в текущий список

- **Что решено:** FAB «+» на экране текущего списка покупок больше не переводит пользователя во вкладку «Товары». Вместо этого открывается отдельный экран «Добавить в список» (AddToListScreen) — самостоятельный поток быстрого добавления позиции. На экране пользователь: (1) выбирает магазин или оставляет «Без магазина» (по умолчанию); (2) ищет существующий товар из базы или вводит новый; (3) для нового товара управляет флажком «Сохранить в базе товаров» (по умолчанию включён); (4) при снятом флажке товар создаётся как временный (isTemporary=true) и не появляется в общем справочнике товаров; (5) после успешного добавления экран автоматически закрывается через флаг `shouldNavigateBack = true` в состоянии — `LaunchedEffect` вызывает `onNavigateBack()`, и пользователь сразу видит обновлённый список. Ручная навигация назад через стрелку в TopAppBar остаётся доступна для отмены.

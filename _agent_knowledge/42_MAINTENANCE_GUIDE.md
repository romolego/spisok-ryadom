# Сопровождение и проверка

## Начало задачи

Открыть AGENTS →11/03 →01 →41, затем профильный документ. Работать из корня репозитория. Проверить `git status`; не удалять чужие/неопубликованные изменения, не подменять текущий код старым source ZIP. Пользователь разрешил автономное завершение необходимых шагов; не запрашивать повторное согласие уже порученной работы.

## Среда и команды

Проект использует Kotlin/Compose, Android Gradle Plugin, KSP и Room. Версии зависимостей — в build.gradle.kts и app/build.gradle.kts. JDK17+, SDK35, minSdk26; Gradle Wrapper8.13. На данном ПК SDK/Gradle/JBR уже настроены в local.properties и tools/verify-local.ps1; эти машинные пути не переносить в код приложения.

```powershell
.\gradlew.bat :app:testStandardDebugUnitTest --console=plain
.\gradlew.bat :app:assembleParallelRelease :app:lintParallelRelease --console=plain
```

Для полного локального прогона можно использовать `tools/verify-local.ps1`. `--offline` допустим только при наличии всех зависимостей в локальном кэше. Один Gradle за раз; не запускать конкурирующие тесты над общими native SQLite ресурсами. В build-файле тесты изолируются `forkEvery=1`, `maxParallelForks=1`, heap768m, чтобы избежать Windows native-finalizer ошибок между sandbox.

Для узкой проверки использовать Test.include конкретных class-файлов через временный init script, а не запускать все75 workers с фильтром, который даст пустые классы. Временные scripts/логи — только .local. Проверка должна подтверждать фактические записи/связи, а не повторять реализацию.

## Как выбирать проверку

| Изменение | Минимально нужные сценарии |
| --- | --- |
| Назначение магазина/точки | AUTO/NONE/EXPLICIT, доступность, город, приоритет, удалённое место, открытая карточка |
| Массовая команда | Несколько ID, общий/несколько магазинов, stale ID, отказ без частичной записи, дедупликация избранного |
| Карточка | Save/Back, autosave on/off, raw recovery, пустое имя, внешняя правка, generation после restore |
| Преднастройка | Общий default, основной магазин, явный recipient/None, мгновенный Save, существующий товар, FK delete |
| Целевой список | Один владелец, showInPurchases без копий, перенос, быстрый/каталожный товар, цена/единица, delete |
| Полная копия | Новый/старый формат, повреждённый ZIP/JSON, неверные типы и ссылки, атомарность, фотографии и настройки |
| Переносимый план | Text/JSON round-trip, количества/единицы/места, заметка/комментарий, preview, неизвестная версия |
| Виджет | Те же строки/отметки, grouping/шрифт/отделы, открытие и добавление; OEM отдельно на телефоне |
| Только документация/публикация | Проверенные исходники/APK по хешам, ссылки, архивы, секреты и повторное скачивание опубликованных файлов |

UI-тесты: искать актуальный элемент меню, учитывать несколько одинаковых подписей и отложенное создание LazyColumn-элементов. Сначала прокрутить родитель к нужному узлу, затем действовать. Не менять продуктовую логику ради упрощения теста. После теста закрывать scenario/ViewModel, дождаться освобождения mutex и только затем закрывать Room.

## Миграции и форматы

Текущее состояние: Room16, экспорт ZIP12. Старые схемы1–16 и тестовые fixtures сохранять. Изменение Entity требует новой миграции и схемы, без destructive migration. Проверять FK, значения по умолчанию и сохранение старых ID/порядка/связей; дополняемый справочник не должен удалять или переименовывать пользовательские категории.

Изменение полного backup и переносимого плана — разные протоколы. Добавление новых полей должно сохранять чтение прежних поддерживаемых версий и отказывать неизвестным будущим версиям/повреждённым данным до изменения базы. Не объединять целевые позиции с регулярными при восстановлении. Не использовать собственные локальные ID импортированного плана как доверенные ID получателя.

## Выпуск

1. Обновить versionCode/versionName только для новой продуктовой сборки. APK0.17 при этой публикации не пересобирается.
2. Выполнить соответствующие проверки; для функционального релиза обычно полный регрессионный набор, release и lint.
3. Зафиксировать source/test/schema/build seal, JUnit, логи, результаты lint и ограничения проверки. Изменение приложения после тестов требует новой соответствующей проверки. Уточнение только старого тестового контракта допускает отдельную перепроверку класса при побайтно прежнем production-коде; оба набора доказательств сохранить и явно описать.
4. Проверить APK: package, versionCode/name, русский label, min/target SDK, отсутствие debug-флага, прежний сертификат и SHA256. Пересборка без прежнего локального ключа не является обновлением уже установленного приложения.
5. Подготовить публичные артефакты из Git-коммита: исключить реальные экспорты/фото, ключи, local.properties, credentials, hostname/служебные потоки JUnit и локальные персональные пути. Синтетические fixtures оставлять воспроизводимыми.
6. По прямой авторизации пользователя опубликовать ветку/PR, слить без переписывания истории, выпустить тег и draft→public release. Повторно скачать каждый файл без авторизации и сверить SHA256. При расхождении не сообщать о завершённой публикации.
7. Обновить01/08/09/12/13 и профильные знания; указать source commit, release URL, результаты и что не проверялось.

## Непубличные файлы

.local/signing — прежний ключ; .local/private — личные базы; .local/artifacts — все локальные выданные результаты; .local/verification — исходные доказательства. Не делать `git add -f` для этих папок. Приватный рабочий архив не заменять публичным, очищенным от деталей. Файлы прежнего чата сохранены, но следующий цикл разработки не должен зависеть от его cwd.
